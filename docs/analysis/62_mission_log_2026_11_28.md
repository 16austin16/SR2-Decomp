Highlights worth knowing before porting:

* **`0x703190` + `0x701B70` / `0x701BA0` / `0x72E0B0`**: the collector classes (`havok_all_ray_hit_collector`, `havok_all_linear_cast_collector`, `havok_custom_character_collector`) embed a small array of 12-byte hit entries
  (capacity 8, 0x80 or 0x100). Their constructors call `vector_constructor_iterator` (0x402450) with the element constructor `0x703190` (`{-1, -1, 0.0f}`). 85 game samples all sit on the three instructions of that
  constructor, i.e. every ray / shape cast constructs and fills 128-256 entries. A cheaper design (lazy init) would be a real saving; as a port it is a three-store leaf.
* **The render-list sort cluster 0x52B000-0x52DE10** (16 functions, 225 render samples in the new run, 106 in `std_rotate_render_items` alone): MSVC `std::stable_sort` instantiations over the 20-byte render items of the
  nine render lists (the item is `{instance, flags, ...}` as in `render_list_add`), one per comparator (`render_item_less` 0x5240F0, the second comparator at 0x52D080 / 0x52D300, and a callback variant). Thunks at 0x52B000 / 0x52B050
  are called from `render_frame`; `render_lists_sort_all` (0x524290) calls the callback variant five times.
* **Trees**: `chunk_trees_submit` (0xA8FAD0) is called from `render_stage1`; 202 render samples. It loops every streamed chunk, then every tree (0x14-byte defs, 0x54-byte instances) with distance gates, then queues
  jobs (`.\trees\trees.cpp`) or billboards (`tree_billboards_draw_all`, `tree_billboard_quad_draw`, `gfx_draw_billboard_sprite` 0xD10510, shared with the glares and `world_text_render`).
* **Particles**: `particle_vertices_build` (0xCFC550, 0xC50 bytes, only caller `r_particle_inst::pre_render`) writes the vertices of the six particle types into `dynamic_vertex_alloc` memory (stride 0x14 / 0x18 / 0x1C, at most 500 particles per call);
  `particle_batch_draw` (0xCFD7B0) draws them with `misc-static.tga`. These go through the upload memcpy of doc 58 section 3.
* **Shadows**: `shadow_maps_build` (0x5380A0) -> `shadow_caster_bounds_collect` (0x536BD0, 102 render samples) scans the whole render list (20-byte items, 0x2784990 entries) once per frame for casters (instance type 4, flag 0x10000)
  and unions their bounds (`aabb_union_in_place` 0xBF52D0, `shadow_bounds_list_add` 0x536310).
* **City fade**: `city_instance_fade_gate` (0x4B8C60, 150 samples: 26 game / 124 render) decides per instance whether to run the timed fade-in or fade-out (`0x4B8890` / `0x4B8A50`, both call `timer_elapsed_ms`).

## 5. Open items

* The exe does not hold the display name of tss03; if the game files hold the mission table, a name for the five phases would help the next log (add a F8 label for the last stretch, `Mission ended` did not mark the failure / success dialog).
* `__VEC_memcpy_fastcopy` (59 percent of the render thread in play) is still unexplained beyond doc 58 section 3; the hook idea given there (log `[0x2305948]` / `[0x252A340]` at `dynamic_buffers_upload` and a caller histogram on `_memcpy` for length >= 0x100) would settle it and is now the best-value measurement.
* Names marked `named` in the CSV are inferred from callers, callees and frames; the Havok internals (`hkp_solver_*`, `hkp_toi_*`, `hkp_pred_gskf_*`) were not read to the end and should be re-checked before they are used in a port.
* The `0x703190` constructor loop is the one clear algorithmic waste found: three collector classes construct 8 / 128 / 256 entries per cast, 85 game samples (0.4 percent) in one function. A port can make it a single `rep stosd`-style fill without changing behaviour.
